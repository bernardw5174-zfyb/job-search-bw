# 投递流程框架（国内版）

> 回答"投递动作怎么执行才不犯错"。覆盖：投递记录、重复投递检查、反馈跟踪闭环。
> 路线：投前查重 → 投时记录 → 投后跟踪。范式：投递是实验不是动作，记录才有数据。实现：投递记录表 + 查重动作 + 状态流转。

## 适用场景

- 进入精准投递阶段（每天2-3家），需要跟踪每家状态
- 多平台同时投（BOSS/猎聘/前程无忧），担心重复投同一岗位
- 猎头渠道多，分不清哪些推的是同一家

## 核心认知

**投递记录 = 求职实验的数据表**。没有记录就没有响应率、没有面试漏斗、没有方法论迭代的依据。

**查重是投递纪律不是洁癖**：重复投递同一岗位（尤其跨平台）会被 HR 视为不专业/海投，印象分直接扣。低成本查重 > 事后补救。

## 三条纪律

### 1. 投递记录（投时顺手记）

- 每次投递补一行：日期 / 公司 / 岗位 / 渠道 / 简历版本 / 状态 / 备注（薪资、匹配度、风险）
- 记录时机 = 投递动作发生时，不事后回忆（会漏）
- 公司未披露（猎头岗）时，记"猎头机构 + 薪资量级 + 岗位名"，为查重留线索

### 2. 重复投递检查（投前/记录时）

记录前查三个盲区：

| 盲区 | 怎么查 | 命中处理 |
|------|--------|---------|
| 跨渠道重复 | 同公司同岗位在 BOSS/猎聘/51job 都发过，可能已投 | 提醒：这家投过了，别再投 |
| 猎头岗重复 | 不同猎头推同一家（尤其"未披露"的），岗位名+薪资量级比对 | 提醒：疑似同一家，先问猎头公司名 |
| 列表页重复 | BOSS 搜索列表页多次抓取，同一岗位出现在多个文件 | 按岗位名去重，归档时只保留一份有效 JD |

### 3. 反馈跟踪（状态流转）

**状态流转以下方「状态枚举说明」9 档主链为准**（已投递/已打招呼 → HR查看 → HR联系/要简历 → 面试邀约 → 不合适·拒绝/停止招聘/放弃）；早期五态图（已投递→HR查看→HR联系→面试→Offer/失败）已并入 9 档，不再单独使用。

- 状态变化（对方查看/联系/要简历/约面/拒绝/停招）→ 更新对应行状态（取当前最高已发生节点）
- 每周汇总一次响应率，喂给实验日志；⚠️ **响应率是弱指标**（拒绝/中性也算响应→虚高，见假设注册表 #13），真正推进看要简历率/面试邀约率

#### 状态枚举说明（2026-09-30 增，模板配套）

**一、主链状态（模板「状态」列推荐取值）**

| 状态 | 含义 | 触发动作 |
|------|------|---------|
| 已投递 | 简历已发出（直投/打招呼后对方索要并发简历） | 记一行 |
| 已打招呼 | 仅发了打招呼文本，对方未索要简历（BOSS 类平台） | 记一行，简历版本写「未提供（等要简历）」 |
| HR查看 | 平台后台显示 HR 已读/已查看 | 更新状态列 |
| HR联系 | HR 主动回复/交换微信/约时间 | 更新状态列，备注记联系方式 |
| 要简历 | 对方索要简历（打招呼后） | 更新状态列，追加「已发」 |
| 面试邀约 | 收到面试安排 | 更新状态列，备注记面试时间/形式 |
| 不合适/拒绝 | 平台显示「暂不合适」或 HR 明确拒绝 | 更新状态列，备注记拒绝原因（若有） |
| 停止招聘 | 岗位下架/停招 | 更新状态列，停止跟进 |
| 放弃 | 自己决定不投/不跟进 | 更新状态列，备注记放弃原因 |

**二、平台后台状态语义（三平台后台可观测的真实状态，2026-09-30 实测）**

| 平台 | 可观测状态 | 说明 |
|------|-----------|------|
| BOSS直聘 | 送达 / 已读 / 回复 | 「沟通」列表只保留约 **30 天**，超窗会话永久消失——每周必须回填，否则样本丢失 |
| 猎聘 | 已投递 / 已查看 / 面试邀约 / 暂不合适 / 停止招聘 | 应聘记录全量留存，可随时回溯 |
| 前程无忧 | 已查阅 / **感兴趣** / 邀面试 | 「感兴趣」是 HR 主动标记，强于「已查阅」，判响应率时单独计一档；我的申请只保留约 **60 天** |

**三、口径纪律**
- 状态以**平台后台实际显示为准**，不靠记忆/口头估算（后台是事实，快照是推论）
- 直投记录（应聘记录页）与打招呼记录（IM/沟通）是两套数据源，响应率分开算，不混
- 猎头岗未披露雇主时，备注记薪资量级（查重线索），不虚标
- **状态列记录当前最高已发生节点（状态快照），不要求保留历史状态**——9 档不是严格互斥的生命周期：如「HR 联系了但未要简历」，状态列填「HR联系」即可，联系内容写入备注；「HR 联系后又要了简历」，状态列更新为「要简历」，过程记备注
- 备注列建议记「直投/打招呼」动作——同一「已读」，直投代表简历被打开、打招呼代表消息被读，反馈含义不同（跨平台口径不可比，见假设注册表 #12）

### 4. 版本冻结纪律（2026-09-23 增，独立测试暴露"版本碎片化让复盘失效"）

**投递是实验，实验必须控制变量——简历版本就是变量。**

- **锁定单一版本连投 ≥20 条再复盘**（框架"记录 20 次后汇总"门槛的前提）：复盘前先做**版本一致性校验**——统计已投记录里各版本分布，若有效样本（当前版本）不足，**任何"投了没回音"都不能归因到简历**（既不能证明简历有问题，也不能证明没问题）
- 确需改版：改版前后**各自凑够样本、分开统计**，不要把两版混在一个响应率里
- 不为单个岗位临时换版（实测教训：7 条触达用了 6 种版本，v1.8 仅 2 条 → 有效样本 2 条，整轮复盘归因失效）

## 输出格式

投递记录表（**位置：`00-raw/投递记录/投递记录表.csv`**——复制 `03-实战/templates/投递记录表.csv` 到私人工作区，**不进公开仓库**）：

```markdown
| 日期 | 公司 | 岗位 | 渠道 | 简历版本 | 状态 | 备注 |
|------|------|------|------|---------|------|------|
| 08-05 | XX公司 | 岗位名 | BOSS | v2.1 | 已投递 | 匹配度85% |
```

## 陷阱

- ❌ 记录时靠回忆——投完立刻记，隔天就忘（实战教训：补记录时差点重复补一行）
- ❌ 只记投递不记状态——没有反馈跟踪，响应率算不出来
- ❌ 猎头岗不记薪资量级——两个猎头推同一岗位时无从判断是不是同一家
- ⚠️ 投递记录是个人数据，**不进公开仓库**（零个人信息原则），存私人工作区；本框架是方法论，可对外

## 与其他框架的衔接

- 记录 20 次投递后汇总响应率 → 反哺《关键词情报框架》验证简历关键词改动是否有效
- 响应率数据 → 反哺假设注册表（验证机制的数据来源）
- 面试环节 → 复盘记录在自己的工作区（面试线待发布）

## 来源与适配说明

1. **原方法论出处**：国内实战提炼（个人求职实验），无直接外部方法论来源；"投递是实验不是动作"的范式与常见求职实验方法论同构（公开内容）。
2. **本地适配改了什么**：
   - 针对国内三平台（BOSS/猎聘/前程无忧）多通道投递场景，新增**三盲区查重**（跨渠道/猎头/列表页）——国内平台多、猎头中介多的特有风险；
   - 状态漏斗定为"已投递→HR查看→HR联系→面试→Offer/失败"——对齐国内平台后台可观测的状态流转（BOSS 沟通记录/猎聘应聘记录/51job 我的申请）；
   - 强调"公司未披露的猎头岗记薪资量级"——国内保密招聘常见，为查重留线索。
3. **已证伪 / 已删除的部分**：无（本框架为国内实战提炼，未引入需证伪的外部假设）。
4. **适用边界**：本框架的查重纪律与状态漏斗已验证（假设注册表 #11 ✅）；"每周汇总响应率"节奏为个人实践习惯（每天 2-3 家、每周汇总），使用者可按自身投递量调整。投递记录表属个人数据，公开仓库只提供方法论与模板，不收集任何投递数据。
5. **内部统计模型与公开操作模板的关系**：本包公开模板是**操作层投影**——自然语言 9 档，追求可理解、可执行；维护方内部另有**统计层投影**（动作与阶段分离的受控枚举、判据可机械复现），用于渠道有效性统计，**不公开复制**。两套是同一事实的不同抽象层；内部治理结论（如 #12/#13 的口径修正）仅以本注册表公开版的形式对外。

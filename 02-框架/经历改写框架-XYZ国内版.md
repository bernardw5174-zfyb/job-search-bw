# 经历改写框架（XYZ 国内版）

> 把"我做了什么"改写成"我带来了什么结果"。基于 Google XYZ 公式的中国化版本。
> 路线：拆解每条经历 → 套 XYZ 结构 → 业务语言过滤。范式：先业务结果，后技术手段。实现：公式 + 强动词 + 精确数字。

## 适用场景

- 技术背景转型业务岗，简历叙事偏技术实现
- 经历写得像岗位描述（"负责XX"），没有结果
- 简历 6+ 页太长，需要浓缩

## 核心公式

### Google XYZ → 中国版

| 维度 | 原版（英文） | 中国版 |
|------|------------|--------|
| 公式 | "Accomplished [X] as measured by [Y], by doing [Z]" | "通过[Z方法]，实现[X结果]，[Y指标]提升XX%" |
| 开头禁忌 | Responsible for / Helped with / Assisted in | 负责 / 参与 / 协助 |
| 强动词 | Led, Drove, Built, Optimized | 主导, 推动, 搭建, 优化 |
| 废话词 | various, multiple, successfully | 赋能, 抓手, 闭环, 助力 |
| 数字要求 | 每条必须有数字 | 同——必须精确，不用概数（"50万元"不写"十万级"） |

### 每条经历的标准结构

```
[业务场景/背景痛点] → [你的角色] → [具体动作(数字化手段)] → [可量化业务结果]
```

**关键：先写业务结果，技术手段一句话带过。** 目标岗位的面试官是业务负责人/HR，不是技术负责人——他们能看懂的术语才保留。

## 三条线并行结构（转型者杀手锏）

能同时描述业务策略和技术落地的经历是最强卖点。用 bullet list 同时铺开：

```
- 业务策略：（具体运营动作）
- 技术落地：（基于业务需求驱动系统迭代）
- 项目管理：（协调、推动、复盘）
```

## 改写规则

1. **叙事从"我做了什么系统" → "我帮业务解决了什么增长问题"**
2. **每条技术能力后面跟一句业务价值**（"裂变K因子>1" → "老客带新客实现自增长，不花钱买量"）
3. **最近 3 年经历占 50% 篇幅**（面试官最看重）
4. **10 年以上的经历压到 3-4 行**（对业务岗没用）
5. **负面经历主动改写叙事**（项目下线 → "从0到1的探索经验"）
6. **量化必须精确**：明确抵触"十万级""接近50%""上千"这类近似表述。必须用精确数字。如果只给了范围，追问精确值。简历上的每个数字必须是硬数据，不是概数。
7. **行业参照必须查证**：⚠️ 教训（2026-08-04）——曾随口说"OTC会员销售占比行业普遍20-30%"支撑简历数字，查证后发现连锁药店行业实际约 70%（中国药店 2025 年刊/某头部连锁年报 77%）。**任何用于支撑简历数字的行业参照，必须先查证来源并记录**；查不到可靠来源就不引用，用自身趋势做参照。
8. **"核弹头+真实信号"混合数据**：
   - 核弹头数据：项目上限/全量口径数字，第一眼冲击力（"招募10000+会员，销售额100万元"）
   - 真实信号数据：实际运营指标，细节可信度（"会员销售占比从33%提升至37%"）
   - 两者缺一不可：核弹头让 HR 停住多看几秒，真实信号让 HR 觉得"这人不是编的"

## 关键词分层（keyword layering）

改写时把《关键词情报框架》的产出分层嵌入：
- table-stakes 词 → 摘要 + 核心业绩第一屏（必须出现）
- differentiating 词 → 核心业绩 + 项目描述（有则加分）
- 趋势词 → 择机嵌入（不硬塞）

## 业务语言过滤（HR-consumption 检查）

❌ **不要写（HR 看不懂）**：
- 数据引用开场（"2026年Bain数据显示…"）
- 内部阶段术语（"阶段01/02/03"）
- 技术架构细节（RAG、vLLM、multi-step推理、推理引擎）
- 系统设计名词（四层架构、知识路由、source boost）
- 项目内部编号/版本号

✅ **要写（HR 能看懂）**：
- 一句话定位：项目做什么、解决谁的什么痛点
- 你的角色：方案设计+落地负责人
- 具体动作（业务语言）：每条工作写"带来了什么效果"
- 可量化的结果：具体数字
- 行业关键词：HR 搜索用的词

## 优势亮点三颗子弹策略（"三个靶心"原则）

当目标岗位强调 AI 转型落地能力时，优势亮点段落三条子弹分别打不同靶心，展示不同能力维度：

| 子弹 | 打什么靶心 | 示例 |
|------|-----------|------|
| 第1条 | **业务创新** — 能判断方向、有首创/独家项目 | AI重构购物决策路径 + 行业首创联合会员 |
| 第2条 | **数字化规模** — 业务底座大、数据硬 | 门店激励覆盖 95%+ 连锁网络、10万+ 一线人员、500万+ 激励金额（示意值） |
| 第3条 | **AI横跨落地能力** — 多个项目都嵌入了AI，不只是做一个 | 门店激励（AI凭证审核）、巡店（AI图像识别）、联合会员（AI决策路径重构）三项目独立完成场景识别到落地交付 |

**为什么必须横跨多项目**：HR 看到第3条时，脑补的叙事是"这个人不是只在旗舰项目里用了 AI，而是每个项目都主动嵌入了 AI"——这是"AI原生的业务人"和"做了一个AI项目的人"的关键区别。

**三条子弹分配规则**（实战经验）：
- 优先选用**高知名度公司**战绩（知名集团/行业头部），知名度弱的公司项目嵌入工作经历正文，不适合做开篇定位钩子
- 优先**近期项目**（最近5年内），10年前项目对业务岗说服力不够
- 三条子弹展示**三个不同维度**（模式创新 + 团队管理 + 数字化提效），分量要等同——不能两条战略级、第三条像单个运营活动
- 对某条规模担忧（"懂行的人觉得很小"）→ 果断换角度：从"项目规模"切到"业务流程数字化改造的owner视角"
- **品牌价值锚点**：优先把知名品牌名嵌入每颗子弹（如"某头部集团实施落地 CRM 系统"）——品牌名是HR第一时间停住目光的信用信号

## AI-native 项目叙事模式

传统数字化项目（CRM/会员运营/SFE）中嵌入了 AI/Agent 能力时，把项目包装为 **AI-native 叙事**而非"做了个系统"。

### 三层叙事结构

```
┌──────────────────────────────────────┐
│ ③ AI Agent 层（最外层）               │
│   决策自动推理、多步协作、知识库编排     │
├──────────────────────────────────────┤
│ ② AI 能力层（中间层）                  │
│   OCR/图像识别/自动审批/数据模型 等     │
├──────────────────────────────────────┤
│ ① 业务数据层（基底）                   │
│   会员体系/促销规则/门店数据 等         │
└──────────────────────────────────────┘
```

**叙事重心在③，用②举例，①做支撑。** 不让①抢篇幅——业务数据是基础，但卖点是 AI 如何改变了业务。

### 传统语言 vs AI-native 语言对照

| 传统描述 | AI-native 改写 |
|---------|---------------|
| 搭建了CRM会员体系，打通品牌-渠道数据 | 构建AI Agent感知的会员数据基础设施，使Agent可跨数据域推理 |
| 系统实现店员激励自动发放与对账 | 部署AI凭证自动化审批Agent，替代传统审核流程 |
| 用OCR识别小票，数据汇总到后台 | 部署AI图像识别Agent执行终端陈列检查与竞品情报采集 |
| 搭建数据看板追踪运营指标 | 构建决策支持Agent，自动聚合多维度数据辅助运营决策 |
| 做了个项目知识库 | 构建可复用的AI项目知识基础设施（知识库+服务商智能体） |

### 落笔方式

项目描述**前两句**就打 AI-native 叙事，不藏在最后。强制自检（展示前逐条过）：
- [ ] 没有数据研究引用（Bain/McKinsey 等）→ 趋势一句话结论即可，不带出处
- [ ] 没有内部阶段术语（阶段01/02/03）
- [ ] 没有技术架构细节（RAG/vLLM/PG+Redis/multi-step推理/推理引擎）
- [ ] 没有系统设计名词（四层架构/知识路由/source boost/确定性函数）
- [ ] 没有 ROI/投资回报率（示例偏好：简历不写 ROI）
- [ ] "智能体"角色定位正确：服务商的项目助理（帮理解/帮生成/帮对齐），不是替人执行
- [ ] "从0到1推动"列出全部参与方（不能只写一个）
- [ ] HR 10秒能扫完，不需要行业技术背景

**AI叙事深度跨项目一致**：3个核心项目且优势亮点说"AI横跨多项目"时，每个项目的 AI 描述深度必须接近——项目A全文AI叙事、B/C只一句话"引入AI"会产生信噪比问题（HR感觉AI只集中在项目A，B/C是硬贴标签）。每个项目至少在职责/业绩中有一句具体的 AI 设计或落地动作，且展示不同 AI 展开场景。

**"重新定义项目方向" vs "落地成果"归属**："重新定义项目方向"是项目定位/洞察层面 → 放落地成果或背景概要；"核心工作"下面只放具体做的**动作**（搭建/设计/推动）；"落地成果"放动作带来的**结果**（方案获认可/对接完成/框架输出）。

## 改写纪律强化（借鉴 career-ops Source-of-Truth + ai-job-search Backtrack Test，均为公开 GitHub 项目）

> 改写框架解决"怎么写"，本节解决"写到什么程度算过头"——改写与编造的分界线。

### 1. Interview Backtrack Test（改写边界测试）

改写后的每条 bullet 模拟面试追问——候选人能否不改口解释？如果面试官一问，他得说"我其实想说的是……" = 过头了。

| 档位 | 允许吗 | 例子 |
|------|--------|------|
| ✅ OK | 重排经历顺序突出相关、用目标域自然同义词、强调宽泛角色中某一面 | 把最相关项目提前；"会员运营"↔"用户分层" |
| ⚠️ FLAG | 学术+行业经验合并成一条暗示全是行业、用 JD 术语描述相邻但不同的工作 | 把培训讲师经历并入企业工作经历 |
| ❌ Never | 声称没有的经验、暗示没做过的领域 | "主导AI Agent落地"但实际只是用了AI工具 |

**落笔规则**：落入 ⚠️ 档的 bullet 改完后主动呈报候选人："这条是拉伸，因为X。保留/软化/删？"——不替用户决定。

### 2. 指标禁止硬编码（Source-of-Truth）

简历/表单里的所有数字评估时从事实源（简历原文/项目事实）现读，不允许凭记忆硬写——"好像有个数"不算数。同"加词必须验证事实"纪律。

### 3. 工具混淆禁令

用过某工具 ≠ 造了某工具（career-ops 说这是最常见的编造模式）。简历只写事实源明确归属的产出。例：用了某 SaaS 平台 ≠ 搭建了该平台。

### 4. 产出验收四层清单（借鉴 ai-job-search Verification Checklist）

每次产出 CV/求职信后，交付前逐层过：

| 层 | 检查什么 |
|----|---------|
| ① 事实层 | 所有 claim 有事实源；公司类声明独立验证过（不信 JD 内 URL） |
| ② 定向层 | 摘要/开头段针对具体岗位定制（非通用）；缺口诚实承认（不藏） |
| ③ 一致层 | 简历/在线简历/表单答案内容无矛盾、语气一致 |
| ④ 质量层 | 投递版 DOCX/PDF 真实打开检查（不能只看 md 没问题）；文本层可复制（HR 会转发/提取文字） |

## 输出格式

```markdown
## 改写建议：[目标岗位] · [资历]

### 整体评价（1-2句）
...

### 每条经历改写示例
**原：** ...
**改：** ...
**为什么：** ...

### 待用户补充的数据
- 第X条经历需要补充：会员数/销售额/转化率（具体数字）
...

### 下一步
- 用户补什么 / 我出什么
```

## 陷阱

- ❌ 一次性给出最终版——用户需要参与决策（2-3 轮迭代是正常节奏）
- ❌ 改用户没有要求改的内容——用户说"看新加的这条"，只改这条
- ❌ 添加用户没写的内容——缺失的信息用问题提出，不写进草稿
- ❌ 删除经历前不澄清意图——用户问"这个合适吗"可能是位置问题，不是想删除
- ❌ 改 title（违法/背调会挂）——可以建议更贴切的职能描述，不能改职位名
- ❌ 用"AI系统方案"类技术表述——业务岗 HR 会归到 IT 池子，直接 pass
- ❌ 在简历文档里放个人信息/头像——平台注册时填写，平台自动拼接

## 与其他框架的衔接

- 输入来自《简历诊断框架》的 Top 5 修复 + 《关键词情报框架》的关键词清单
- 改写完交给《模拟面试框架》验证（面试官会追问每个数字）

1. **原方法论出处**：
   - **Google XYZ 公式**（公开可得：Google 官方简历指导）——本框架的核心公式来源；
   - **career-ops**（公开 GitHub 项目）——借鉴 Source-of-Truth（指标禁止硬编码）与"工具混淆"鉴别；

2. **本地适配改了什么**：
   - 公式从英文直译改为中文语序："通过[Z方法]，实现[X结果]，[Y指标]提升XX%"；强动词/废话词替换为国内简历语境；
   - 新增"三条线并行结构"（业务策略+技术落地+项目管理）——服务国内转型候选人的"复合型"卖点；
   - 新增 AI-native 叙事模式与三颗子弹策略——对应国内 2025-2026 AI 转型岗的实际 JD 语言（AI Agent 落地/应用场景识别为高频词）；
   - 新增"行业参照必须查证"纪律（见下，来自实战教训）。
3. **已证伪 / 已删除的部分**：
   - 行业参照未查证即引用（曾称"OTC 会员销售占比行业普遍 20-30%"，查证后实际约 70%，来源：中国药店 2025 年刊/某头部连锁年报 77%）——该做法已删除，改为"查不到可靠来源就不引用"；

4. **适用边界**：本框架针对国内业务岗（HR/业务负责人筛选）；纯技术岗/海外 ATS 环境另有范式。XYZ 公式中国版仍在验证中（假设注册表 #6，⚠️ 验证中——改写版投递样本收集中），"三颗子弹/AI-native 叙事"为实战提炼，样本量有限，属方向性经验。
